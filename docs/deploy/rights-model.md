# Модель прав Распаковщика и гейты деплоя (§7.3 + §7.5)

Короткая шпаргалка для владельца сервера и для ревью. Подробный протокол — в скиллах мозга
(`brains/unpacker/.claude/skills/`), здесь только устройство и почему оно такое.

## Главный принцип: LLM предлагает — код исполняет

Мета-агент «Распаковщик» — обычный агент движка. Он собирает данные, показывает план и ждёт
«да». Всё, что меняет систему, делают детерминированные скрипты с собственной валидацией.
Поэтому «уговорить» деплой невозможно: проверки — это код в `deploy/deploy.sh`, а не абзац
в промпте, который модель может пересказать по-своему.

## Гейты §7.3 — что именно проверяет код

Блок гейтов печатается человеку и гоняется **всегда**: и при `--dry-run`, и при
`--skip-preflight` (флаг про окружение, а не про гейты). Отказ = код возврата 3.

| Гейт | Зачем |
|---|---|
| контур auth выбран (`--auth-mode`, `--audience`) | внутренний контур — своя подписка, клиентский — только API-ключ |
| клиентская поверхность на подписке = отказ | обслуживать третьих лиц с подписки запрещено ToS и энфорсится |
| клиентская поверхность целиком = отказ | нет ToolPolicy/LimitsPolicy (Фаза 4) → fail-closed, а не «на честном слове» |
| для API-контура заданы лимиты | pay-per-token без потолка = счёт на любую сумму |
| контуры не смешаны | один инстанс — один контур (§8.1) |
| мозг существует и в нём `CLAUDE.md` | опечатка в пути раньше уходила в `git clone` и падала после провизии |
| рабочее дерево git-мозга чистое | иначе следующий `git pull` встанет и идемпотентность умрёт |
| имя инстанса ↔ бот 1:1 | иначе имя, каталог и логи начинают врать про то, чей это бот |
| токен не занят другим инстансом | два polling'а на один токен = 409 у обоих, оба теряют сообщения |
| токен валиден по getMe | в вывод — `[REDACTED]`; сеть недоступна → отказ, а не тихий проход |

Токен уходит curl'у не через argv, а через `--config` (stdin) — иначе он был бы виден в `ps`.

## Права: whitelist вместо sudo

`deploy/sudoers.d/unpacker` — шаблон, который ставит `deploy/install-sudoers.sh`
(рендер → `visudo -cf` → права 0440, идемпотентно). Разрешены ровно:

- `<движок>/deploy/deploy.sh`, `<движок>/update.sh`, `<движок>/deploy/agentctl.sh`;
- `systemctl start|stop|restart|status agent-tg@*`.

Нет и не будет: `ALL`, оболочек (`sh`/`bash`/`env`/`su`/`sudoedit`), wildcard в путях скриптов,
`systemctl daemon-reload|enable|disable` (юниты ставит `deploy.sh`, уже будучи root), самого
`install-sudoers.sh` (иначе агент расширил бы себе права).

### Формы вызова, а не «команда без аргументов»

Команда, перечисленная в sudoers **без аргументов, разрешена с ЛЮБЫМИ аргументами**. Именно
так `update.sh --engine-dir <свой каталог>` превращался в root: скрипт сорсит
`deploy/_common.sh` из указанного каталога, а агент этот каталог контролирует. Поэтому:

- `update.sh` — перечислены ровно `""`, `--dry-run`, `--rollback`, `--ref <тег>`,
  `--dry-run --ref <тег>`. Формы с `--engine-dir` нет;
- `agentctl.sh` — только read-only глаголы (`list`, `status`, `logs`, `health`, `doctor`);
- `deploy.sh` — аргументы динамические (имя, токен, мозг, контур), перечислить их нельзя;
  поэтому он валидирует каждый флаг сам и держит гейты §7.3 в коде;
- `Defaults:<run-user> env_reset, !setenv` — окружение root-вызова задаём мы. Переменные
  агента (PATH, LD_*, наш `UNPACKER_DEV_OWNER_OK`) в root-вызов не текут, и `sudo VAR=… script`
  запрещён. Тега `SETENV` в правиле нет.

## Владение файлами: движок — root, venv — снаружи

**Условие, без которого whitelist бессмыслен:** разрешённые скрипты не должны быть
перезаписываемы юзером агента — иначе он подменит содержимое и получит root даром. Причём
речь не только про сами файлы: право записи в **каталог** позволяет подменить скрипт
переименованием, даже если файл 0555 и принадлежит root.

Раньше здесь был неразрешимый конфликт: `install.sh` отдавал весь движок run-user'у (иначе
`uv sync` не мог создать `.venv` внутри дерева), а модель прав требовала root-владения.
«Работающей» конфигурации не существовало. Развязка — **вынести venv из дерева кода**:

| Что | Владелец | Права |
|---|---|---|
| `/opt/unpacker` (код, скрипты, шаблоны) | `root:root` | `go-w` |
| `/var/lib/unpacker/venv` (`UV_PROJECT_ENVIRONMENT`) | run-user | обычные |
| `~<run-user>/agents/<name>` (инстансы, `.env` 600) | run-user | обычные |
| `~<run-user>/brains/<slug>` (мозги ботов) | run-user | обычные |
| `$TG_RUNTIME/brains/unpacker` (мозг Распаковщика) | `root:root` | read-only для агента |

Следствия, зафиксированные в скриптах:

- `uv sync` и любые git-операции над движком делает **только root** — в `install.sh`/`update.sh`.
  `deploy.sh` код движка не обновляет вообще (раньше он делал `git pull --ff-only` и падал на
  detached HEAD после установки на тег — то есть ломался КАЖДЫЙ деплой);
- run-user получает запись ровно на venv, свои инстансы и свои мозги;
- мозг самого Распаковщика не копируется: он живёт в дереве движка, значит обновление кода
  сразу обновляет и протокол (правки скиллов доезжают до учеников).

Привести машину в это состояние:

```
sudo chown -R root:root /opt/unpacker && sudo chmod -R go-w /opt/unpacker
```

`install-sudoers.sh` это проверяет и **отказывается** ставить права, если каталог или скрипт
принадлежит run-user'у либо доступен на запись группе/прочим (код возврата 3). Единственный
обход — явный флаг `--dev-owner-ok` (стенд разработчика; через `sudo` от агента он не
проходит, `env_reset` стирает и одноимённую переменную окружения).

## Одна вселенная путей: /etc/unpacker/engine.conf

Личность run-user'а и базы каталогов раньше выводились из окружения **вызывающего**
(`TG_RUN_USER` → `SUDO_USER` → `id -un`). Любая команда, запущенная «не так, как это делал
install.sh» — cron, root руками, `sudo` от агента с `env_reset` — читала другую вселенную
путей и тихо рапортовала успех: первый мозг ложился в один каталог, следующие в другой, а
`agentctl doctor` отвечал `NOT DEPLOYED` про живого бота.

Поэтому есть машинный конфиг `/etc/unpacker/engine.conf` (`root:root`, `0644`), который пишет
`install.sh` и читает `deploy/_common.sh`: `TG_RUN_USER`, `TG_RUNTIME`, `TG_AGENTS_BASE`,
`TG_BRAINS_BASE`, `TG_UV_BIN` (+ необязательный `TG_VENV`). Приоритет: **env → engine.conf →
прежний фолбэк**. Конфиг **парсится построчно**, а не сорсится — `source` файла конфигурации
это ровно тот класс дыр, из-за которого правило «команда без аргументов» давало root.

## Юнит Распаковщика

Имя юнита остаётся контрактным — `agent-tg@<name>.service`. Послабление живёт в drop-in
`/etc/systemd/system/agent-tg@<name>.service.d/10-unpacker.conf`
(шаблон `deploy/templates/unpacker-dropin.conf`):

- `NoNewPrivileges=no` — единственное послабление: под ним setuid-`sudo` не работает вообще;
- `ProtectSystem=full` + `ReadWritePaths=/etc/systemd/system /etc/sudoers.d` — /etc только на
  чтение, кроме двух каталогов, без которых деплой физически невозможен;
- `PrivateTmp`, `ProtectKernel*`, `ProtectControlGroups` — на месте;
- `CapabilityBoundingSet` сужен до нужного sudo и провижинингу файлов минимума.

Обычные агенты (`--role agent`) drop-in не получают и остаются под `NoNewPrivileges=true`.

## Что ещё не закрыто

- Энфорс лимитов API-контура — Фаза 4: `deploy.sh` пишет их в `.env`, ядро пока не читает.
- Секреты: у `deploy.sh` есть `--token-file` и `--cc-token-file` (файл 600, читается один раз).
  Ими пользуются `install.sh` и мозг Распаковщика — аргумент `sudo` виден в `ps` и НАВСЕГДА
  оседает в `/var/log/auth.log` и в history root. Старые `--token`/`--cc-token` работают (руки
  человека, тесты), но печатать их ученику или в отчёт нельзя.
- Диагностика: `agentctl doctor` проверяет и наличие `claude` в PATH ЮНИТА у run-user — без
  этого «поднятый и молчащий» бот получал вердикт HEALTHY.
- Песочница файловых tool-вызовов и урезанный ToolPolicy клиентского контура — Фаза 4.
