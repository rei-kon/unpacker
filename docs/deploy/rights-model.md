# Модель прав Распаковщика и гейты деплоя (§7.3 + §7.5)

Короткая шпаргалка для владельца сервера и для ревью. Подробный протокол — в скиллах мозга
(`brains/unpacker/.claude/skills/`), здесь только устройство и почему оно такое.

## Главный принцип: LLM предлагает — код исполняет

Мета-агент «Распаковщик» — обычный агент движка. Он собирает данные, показывает план и ждёт
«да». Всё, что меняет систему, делают детерминированные скрипты с собственной валидацией.
Поэтому «уговорить» деплой невозможно: проверки — это код в `deploy/deploy.sh`, а не абзац
в промпте, который модель может пересказать по-своему.

## Гейты §7.3 — что именно проверяет код

Блок гейтов печатается человеку и гоняется **всегда**: и при `--dry-run`, и при
`--skip-preflight` (флаг про окружение, а не про гейты). Отказ = код возврата 3.

| Гейт | Зачем |
|---|---|
| контур auth выбран (`--auth-mode`, `--audience`) | внутренний контур — своя подписка, клиентский — только API-ключ |
| клиентская поверхность на подписке = отказ | обслуживать третьих лиц с подписки запрещено ToS и энфорсится |
| клиентская поверхность целиком = отказ | нет ToolPolicy/LimitsPolicy (Фаза 4) → fail-closed, а не «на честном слове» |
| для API-контура заданы лимиты | pay-per-token без потолка = счёт на любую сумму |
| контуры не смешаны | один инстанс — один контур (§8.1) |
| мозг существует и в нём `CLAUDE.md` | опечатка в пути раньше уходила в `git clone` и падала после провизии |
| рабочее дерево git-мозга чистое | иначе следующий `git pull` встанет и идемпотентность умрёт |
| имя инстанса ↔ бот 1:1 | иначе имя, каталог и логи начинают врать про то, чей это бот |
| токен не занят другим инстансом | два polling'а на один токен = 409 у обоих, оба теряют сообщения |
| токен валиден по getMe | в вывод — `[REDACTED]`; сеть недоступна → отказ, а не тихий проход |

Токен уходит curl'у не через argv, а через `--config` (stdin) — иначе он был бы виден в `ps`.

## Права: whitelist вместо sudo

`deploy/sudoers.d/unpacker` — шаблон, который ставит `deploy/install-sudoers.sh`
(рендер → `visudo -cf` → права 0440, идемпотентно). Разрешены ровно:

- `<движок>/deploy/deploy.sh`, `<движок>/update.sh`, `<движок>/deploy/agentctl.sh`;
- `systemctl start|stop|restart|status agent-tg@*`.

Нет и не будет: `ALL`, оболочек (`sh`/`bash`/`env`/`su`/`sudoedit`), wildcard в путях скриптов,
`systemctl daemon-reload|enable|disable` (юниты ставит `deploy.sh`, уже будучи root), самого
`install-sudoers.sh` (иначе агент расширил бы себе права).

**Условие, без которого whitelist бессмыслен:** разрешённые скрипты не должны быть
перезаписываемы юзером агента — иначе он подменит содержимое и получит root даром.
На VPS движок держим под root:

```
sudo chown -R root:root /opt/unpacker && sudo chmod -R go-w /opt/unpacker
```

`install-sudoers.sh` это проверяет: writable-скрипт → отказ; скрипт, принадлежащий агенту, но
без права записи → громкое предупреждение (dev-режим).

## Юнит Распаковщика

Имя юнита остаётся контрактным — `agent-tg@<name>.service`. Послабление живёт в drop-in
`/etc/systemd/system/agent-tg@<name>.service.d/10-unpacker.conf`
(шаблон `deploy/templates/unpacker-dropin.conf`):

- `NoNewPrivileges=no` — единственное послабление: под ним setuid-`sudo` не работает вообще;
- `ProtectSystem=full` + `ReadWritePaths=/etc/systemd/system /etc/sudoers.d` — /etc только на
  чтение, кроме двух каталогов, без которых деплой физически невозможен;
- `PrivateTmp`, `ProtectKernel*`, `ProtectControlGroups` — на месте;
- `CapabilityBoundingSet` сужен до нужного sudo и провижинингу файлов минимума.

Обычные агенты (`--role agent`) drop-in не получают и остаются под `NoNewPrivileges=true`.
